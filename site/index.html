The problem

Comprehension is the new bottleneck.

AI can create working software faster than a team can form a reliable mental model of it. The tools we reach for assume knowledge the reader does not have yet: class diagrams assume the object model, dependency graphs assume the libraries, and documentation assumes somebody kept it current.

Every serious decision about a system—whether to change it, operate it, secure it, buy it, or bet on it—rests on somebody's understanding of what it is. Those mental models are getting thinner while the systems get larger and change more quickly.

SysCorpus addresses that gap with a navigable representation of the system, grounded in the system itself. It is not a static drawing and not a chatbot's paraphrase. It is a maintained fact base with human and machine-readable ways into the same evidence.

The system

From source code to a map people can reason with.

The architecture is not maintained as a separate drawing and is not normally rebuilt wholesale. A persistent fact store establishes the baseline, accepts changes, refreshes the affected neighborhood, and republishes the human and machine surfaces from the same current facts.

01

Index the system

Establish a complete baseline for one repository or a solution spanning several repositories.

02

Receive change

A merge, push, webhook, nightly run, or project schedule identifies what changed.

03

Refresh the impact area

Reprocess changed facts plus the dependency and blast-radius neighborhood that may be affected.

04

Publish the update

Refresh the interactive map and machine-readable surfaces from the same fact base.

Continuous loopThe cadence belongs to the project—from every accepted change to nightly or scheduled runs. A full re-index remains available for setup, recovery, or analysis-rule changes; it is not the intended day-to-day maintenance path.
What it can answer

Start with the whole. Follow the question. End at the code.

The interface is layered for readers who need orientation first and technical evidence later. Every lens is a question over the same map, and only appears when the dataset can support its answer.

StructureHow is the system composed?
InventoryWhich dependencies, SDK targets, ports, and external services are present?
FlowHow does a person or request move through the application?
ActivityWhere is code changing, who knows it, and where are the hotspots?
CapabilityWhat can the system do beyond its file structure?
DataWhat entities exist and how do they relate?
RulesWhat business and validation rules are encoded, and where?
DesignWhere is structure under stress, and what could a change affect?
Whole to source

Every file accounted for

A coverage ledger assigns every repository path exactly one disposition. Search, drill-down, code previews, documentation, symbols, tests, and source links carry the reader to the evidence.

Supply chain

Eight manifest ecosystems contribute versions, pin state, direct/transitive scope, SDK targets, vendored code, fixture separation, parse warnings, and an evidence-linked CycloneDX 1.5 SBOM.

Humans and agents

The interactive viewer, ai.json, llms.txt, and twelve read-only MCP tools expose the same architecture to people and AI agents without making either reread the raw repository.

From insight to action

Review without losing context

Annotations can target components, files, and symbols; guided tours stay anchored to code; structured implementation prompts carry reviewed findings into the next piece of work.

Activity, churn, authorship, knowledge islands, change coupling, CI status, version history, and blast radius put structural facts into operational context.

Maps can ship as a single file or lazy detail shards, compose several repositories, run in CI, and publish to ordinary static hosting with optional live monitoring.

The trust model

The map must say what it knows, how it knows, and where it does not know.

A plausible but quietly wrong map is more dangerous than an obviously incomplete one. Completeness, evidence, and cross-surface agreement are treated as data contracts and release gates—not as tone-of-voice promises.

1. A claim is proposed

Static derivation or optional enrichment produces a purpose, relationship, rule, finding, or next step.

2. Evidence is checked

File, line, symbol, manifest, and store references are validated without asking an AI to grade itself.

3. Ground or declare

A supported claim ships. An unsupported clause is narrowed. An unresolved question becomes an honest gap.

Coverage is a ledger
Every repository path is parsed, skipped with a reason, or represented by an explicit pruned-directory record. A silent gap is a defect.
Findings stay inspectable
Cycles, coupling, boundary strength, blast radius, duplication, inconsistency, unreferenced code, and verified intent violations retain evidence and verification status. There is no universal architecture grade.
AI remains optional
The deterministic system works without a model. Enrichment is additive, evidence-bound, provenance-stamped, and marked stale when its supporting code changes.
Publication has a gate
Coverage, claim verification, front-door agreement, attribution, licensing, representation, and comprehension checks run before a public map can graduate.

Where it stands · 27 August 2026

Substantial machinery exists. Public proof is the next threshold.

Status below distinguishes what exists in the repository from what is under validation and what remains required for the public program.

Core and updates

Built foundation

The persistent fact store, content hashing, coverage ledger, multi-repository composition, parser families, and single/split projections are built. Changed files update without re-parsing unchanged files; fuller dependency and blast-radius propagation is the next v2 treatment.

Interactive viewer

Built

Hierarchical graph, eight gated lenses, search, source deep links, code previews, annotations, tours, activity and ownership signals, mobile behavior, live status, and administration surfaces exist.

Machine access

Built

ai.json, llms.txt, and a zero-dependency MCP server with twelve read-only tools are implemented and checked against the same fact store.

Supply chain and SBOM

Built

Eight manifest ecosystems feed the evidence-linked supply-chain view. Each dependency-bearing repository projection emits CycloneDX 1.5 sbom.json.

Security and vulnerabilities

Go-live requirement

Useful inputs already exist: network schemes and edges, authentication patterns, environment variables, secret-shaped inventory, rules, dependency pinning, and CRA hygiene checks. A unified security view and package/version matching against maintained vulnerability feeds, with CVEs surfaced as evidence, are required before go-live and are not claimed as complete today.

Evidence-bound enrichment

Validating

The five-phase engine, completeness contract, independent adjudication, usage ledger, run reports, quality audit, and pause/resume controls are built. Current work is validating full real-subject behavior.

Public maintained corpus

Next threshold

The harness, private preview, attribution and license review, comprehension instrument, and graduation gates exist. No public subject map has graduated, and no subject is announced before its map is ready.

Built now · dependency truth

Inventory, versions, pin state, scope, source evidence, targets, vendored code, and CycloneDX output.

Required for go-live · CVE correlation

Match SBOM packages and versions against maintained advisory feeds and keep those results current.

Permanent boundary · no false verdict

A package-to-CVE match is evidence. Reachability, exploitability, and remediation status require their own support.

What's next

The maps are coming.

Starting soon: live maps of well-known open-source projects.

We will be publishing interactive maps of multiple widely used open-source codebases, beginning shortly and growing over time. Each one is kept fresh on a schedule, stamped with the exact commit it was built from, and held to the same gates: complete coverage, security and supply-chain readiness, verified claims, attribution, licensing, and fair representation of its subject.

We're not announcing the subjects yet. When they arrive, they will be here, and you'll be able to judge the maps against codebases you already know. That's the point.
