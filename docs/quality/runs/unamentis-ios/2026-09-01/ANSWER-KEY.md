# P1 — Senior backend engineer

## P1.1 What is this product, for whom, what are its moving parts?

### Expected answer

UnaMentis iOS is a **voice-first AI tutoring / learning client** for iPhone (Swift 6.0 / SwiftUI,
iOS 18+), with a watchOS 26 companion. It is built for **60–90+ minute hands-free spoken learning
sessions at sub-500ms turn latency**. The user starts a session by tap or by Siri and holds an
interruptible spoken conversation with an AI tutor, either freeform or driven by an imported
curriculum. Audience: learners/students (Knowledge Bowl competition prep is a first-class module);
it is a single-developer, AI-assisted, MIT-licensed open-source project.

The client is a **standalone app with an optional self-hosted backend**. It has zero source-level
dependency on server code.

### Must-appear facts

   `README.md:3`; `CLAUDE.md:17`; `CLAUDE.md:226-229` (E2E turn latency <500ms median, <1000ms P99;

## P1.3 Symptom triage: mid-session the app stops talking back, no error, session looks live, worse on hotel/conference wifi

### Expected answer — the ordered look-list

This is the highest-value question and the source is unusually clean about it. The correct diagnosis
shape: **the app has no mid-session error surface, no keepalive, no network monitoring, and only one
of its four network-backed streaming services has any reconnect logic. A dropped WebSocket therefore
terminates the transcript stream silently while the session state machine stays in its last state.**

**Order to look, with files:**

1. **`UnaMentis/UI/Session/SessionView.swift`** (3,605 lines) — the real provider router and the place
   the session is actually assembled (`configureServices`, roughly `:1488-1840`). Every
   user-visible error in this file is raised at **session start only**: the complete list of
   `showError = true` sites is `:1457, 1688, 1702, 1719, 1735, 1751, 1791, 1833`. **There is no
   mid-session error path at all.** This is the direct explanation of "no error shown, session
   appears live".
2. **The STT WebSocket receive loop.** `Services/STT/DeepgramSTTService.swift:131-157`: on any
   `receive()` throw it logs `logger.error("WebSocket receive failed: \(error)")`, calls
   `cancelStreaming()`, and breaks the loop. No user notification, no retry, no state change
   propagated to the session. Same shape in `Services/STT/AssemblyAISTTService.swift` and
   `Services/TTS/ElevenLabsTTSService.swift`.
3. **Keepalive / ping: absent.** A repo-wide grep for `sendPing`, `keepAlive`, `heartbeat`,
   `pingInterval` returns exactly **one** hit, and it is a comment:
   `Services/STT/GLMASRSTTService.swift:268` ("Keepalive acknowledged"). **No iOS code sends a
   WebSocket ping.** On captive-portal / NAT-heavy wifi, an idle socket is reaped and nothing notices.
4. **Reconnect: exists in exactly one service.** `GLMASRSTTService.attemptReconnection()`
   (`:337-386`) does linear backoff `reconnectDelayMs * attempt` for `reconnectAttempts` tries
   (wired as 3 attempts / 1000 ms in `SessionView.swift:1538-1539`). **Deepgram, AssemblyAI and
   ElevenLabs have no reconnect whatsoever.**
5. **Network monitoring: absent.** There is no `NWPathMonitor` and no reachability layer in the app.
   The single mention is a comment: `UnaMentis/UnaMentisApp.swift:932` — `networkType: .wifi, //
   Would query NWPathMonitor`. (`Core/Watch/WatchConnectivityService.swift:160-166` handles
   *WatchConnectivity* reachability, which is a different thing.)
6. **The session state machine.** `Core/Session/SessionManager.swift` — 8 states (`:15-23`). The
   utterance-completion path is driven by a **silence timer** (`silenceThreshold`, default 1.5 s,
   `:168,186,296,907-913`), not by connection liveness. With a dead STT socket the machine simply
   never leaves its current state; nothing times the session out.
7. **The TTS/STT fallback design and PR #18.** See below — this is the second half of the answer.
8. **Timeouts.** `URLRequest.timeoutInterval` is set in ~40 places
   (`ServerConfigManager` 2/5/10 s, `DeviceDiscoveryManager.swift:205` 3 s,
   `MetricsUploadService.swift:232` 10 s, `ChatterboxTTSService.swift:195` 60 s,
   `OnDeviceLLMModelManager.swift:445-446` 300 s / 3600 s). **The cloud LLM services set none** —
   `OpenAILLMService` uses `URLSession.shared` with the 60 s default
   (`Services/LLM/OpenAILLMService.swift:21,55,73`). URLSession timeouts do not apply to an
   already-established WebSocket that is simply not delivering frames.

### The fallback policy, and PR #18 — must-appear

- **The historical policy was "never show an error when a fallback exists", and it is still the policy
  for STT and for cloud TTS.** In `SessionView.swift`:
  - every cloud STT provider whose key is missing silently becomes `AppleSpeechSTTService()` with only
    `logger.warning` (`:1520-1528, 1544-1546, 1554-1557`);
  - every cloud/self-hosted TTS provider whose key or host is missing silently becomes
    `AppleTTSService()` with only `logger.warning` (`:1568-1605`).
- **PR #18 `fix/no-tts-fallback` reversed this for exactly one case: on-device Pocket TTS.** The merge
  at HEAD (`a5717bf`, parents `75c4d76` "feat(voice): make the single voice pipeline rule enforceable"
  and `834dee0` "fix(session): remove the Apple TTS fallback, fail loudly instead") replaced
  `makePocketTTSWithAppleFallback()` with `makePocketTTS() -> (any TTSService)?` returning `nil` on
  load failure, plus `failSessionStartForUnavailableSpeechEngine()`
  (`SessionView.swift:1443-1470`, error text at `:1454-1457`).
- The rule is now written down twice and **machine-enforced**: `CLAUDE.md:173-202` ("MANDATORY: One
  Voice Pipeline") and `docs/ios/VOICE_PIPELINE.md` (132 lines, added by the same PR). Rule 2: *"No
  automatic substitution of engines… A fallback is only worth having when the degraded state is one we
  would ship, and a system voice is not."* Enforced by `scripts/check-voice-pipeline.sh`, run from
  `scripts/lint.sh` and CI, as a **ratchet** against `.voice-pipeline-baseline` (may only shrink);
  escape hatch `// VOICE-PIPELINE-EXEMPT: <reason>`.
- `.voice-pipeline-baseline` records **52 direct engine constructions across 12 files** as of
  2026-08-15; `SessionView.swift` alone holds **31**. `docs/ios/VOICE_PIPELINE.md:61-77` is the table.
- `docs/ios/VOICE_PIPELINE.md:47-58` is the post-mortem an answer should surface: by 2026-08-15 there
  were **five independent TTS resolution sites** with five different failure policies (core session
  substituted Apple TTS "added, wrongly, in PR #14"; barge-in substituted through a second switch in
  the same file; Knowledge Bowl logged and carried on with a broken engine so it went silent; the
  canonical resolver silently returned Pocket TTS for any cloud provider and never attempted a load;
  a fifth in `KBVoiceCoordinator` was excluded from the build and therefore dead but authoritative-
  looking), and a sixth arrived on the Module SDK branch.
- **The canonical resolver is still dishonest at HEAD.** `TTSProvider.resolveConfiguredService()`
  (`Services/Protocols/TTSService.swift:358-364`) reads `UserDefaults "ttsProvider"`, then calls
  `createLocalService()` (`:344-356`) whose `default:` branch returns
  `KyutaiPocketTTSService(config: .lowLatency)` for **every cloud provider**, never attempts a load,
  and cannot return nothing. `VOICE_PIPELINE.md:112-114` lists fixing this as migration step 2 (not
  yet done). Only three call sites use it: `Core/Audio/AudioTTSCache.swift:61`,
  `Core/Audio/UnifiedAnnouncer.swift:42`, `Services/ReadingPlayback/ReadingAudioPreGenerator.swift:194`.
- **`FallbackLLMService` — the documented "runtime resilience wrapper for the LLM tier chain"

A correct sketch must contain, at minimum:

# P2 — Executive

## P2.1 What does this system do, in board language?

### Expected answer

A voice-first AI tutor for iPhone. You talk to it for an hour or more and it teaches, quizzes and
remembers — hands-free, interruptible, sub-half-second responses. It ships with a competition-prep
module (Knowledge Bowl), a reading-list read-aloud player, curriculum import, to-do and spaced review,
and an Apple Watch companion. Its distinguishing bet is **provider independence**: speech recognition,
speech synthesis and the language model are each swappable between on-device, a machine you own, and
the major AI clouds, so the product can run entirely offline and at zero marginal cost, or at premium
quality on cloud providers, from the same code.

### Must-appear facts

- Voice-first AI tutor; 60–90+ minute sessions; sub-500ms target (`README.md:3`, `CLAUDE.md:17,226-229`).
- iPhone-only, iOS 18+, with a watchOS companion (`project.yml:18,63,183`).
- Swappable providers across three tiers (on-device / self-hosted / cloud) for STT, TTS and LLM
  (`Services/Protocols/*.swift` provider enums).
- MIT-licensed open source, single author, "developed with 100% AI assistance"
  (`LICENSE:1-3`; `CLAUDE.md:17`).
- Status is **pre-beta, not shipped**: version `0.1.0` / `[Unreleased]` (`CHANGELOG.md`), and
  `PRE_BETA_AUDIT.md:28` — "it is not ready for a TestFlight beta or an open-source release."
- Pedagogy is a stated differentiator, not a bolt-on: teachback, productive struggle, spaced
  retrieval (**monorepo docs**, `/Volumes/Studio/dev/unamentis/README.md`).

### Would-be-wrong

- Calling it a shipped or revenue-generating product.
- Calling it an enterprise/multi-tenant SaaS. There is no account system, no auth to the backend, no
  server-side user model anywhere in the iOS repo.

## P2.2 What is critical, and what happens if it fails?

### Expected answer

**Critical path = the voice loop: microphone → VAD → STT → LLM → TTS → speaker.** Everything else is
around it. The client is designed so each leg has an on-device option, which is why the app survives
losing the network and losing the backend — but the *specific* failure that is not survivable by
design is a broken on-device speech engine, and the *specific* failure that is survivable but
invisible is a dropped cloud connection mid-session.

### Must-appear facts

| Component | Has a fallback? | What happens if it fails |
|---|---|---|
| **STT** | Yes, always | Every cloud STT silently degrades to `AppleSpeechSTTService()` — log warning only, no user notice. `SessionView.swift:1520-1557` |
| **Cloud / self-hosted TTS** | Yes | Silently degrades to `AppleTTSService()`. `SessionView.swift:1568-1605` |
| **On-device Pocket TTS** | **No, deliberately** | Session **refuses to start** with an explicit message. `SessionView.swift:1443-1470`; policy at `CLAUDE.md:191-194`, `docs/ios/VOICE_PIPELINE.md:22-28` |
| **LLM** | Yes, chained | on-device → cloud (Anthropic, then OpenAI, then Google) → self-hosted; if none, a user-visible error and the session aborts. `SessionView.swift:1651-1800` |
| **VAD** | On-device only (Silero / FluidAudio) | No network dependency |
| **Backend :8766** | Optional | Curriculum download, KB question packs, TTS cache prefetch, module list, transcript streaming and metrics upload stop. The **voice session itself is unaffected.** `KBQuestionService.swift:123` even notes "Reduced timeout since we have bundled fallback" |
| **Mid-session network loss** | **No handling** | Silent stall — see P1.3 |

**With no network at all:** the app still works if the user is on on-device providers — Apple Speech
or GLM-ASR-Nano on-device or Parakeet for STT, Pocket TTS or Apple TTS for speech, and the on-device
llama.cpp model for the LLM. `STTProvider.requiresNetwork` is false for `appleSpeech`,
`glmASROnDevice`, `parakeetEOU` (`Services/Protocols/STTService.swift`, the `case .appleSpeech,
.glmASROnDevice, .parakeetEOU:` arms); `TTSProvider` likewise for `appleTTS`, `pocketTTS`.
If the user is on cloud providers, STT degrades to Apple Speech and TTS to Apple TTS, so speech keeps
working, but **the LLM has no offline substitute unless a model has been downloaded** — the app shows
"No LLM available…" and aborts (`SessionView.swift:1687-1688`).

**Depends on the backend vs on-device — the honest split:** the backend is a *content and telemetry*
server, not a runtime dependency of the conversation. Nothing in the audio path traverses it.

### Would-be-wrong

- "If the server goes down, the product stops." It does not; conversations continue.
- "Everything has a fallback." Pocket TTS deliberately does not, as of PR #18.
- "The app handles connectivity loss gracefully mid-session." It has no code that does so.
