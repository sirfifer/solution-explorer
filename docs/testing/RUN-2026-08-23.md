# Deterministic validation run, 2026-08-23

What was built, what it found, what was fixed, and what is still open. Written
for the morning, so nothing here assumes you were watching.

## The short version

Two deterministic suites now exist, plus the observability to run them. Pointed
at the real VS Code projection (573 components, 15,366 files, 153,231 symbols)
they found five defects. Four are fixed. The fifth was found by the final
full-depth sweep and is the most serious of the lot.

**Final full unbudgeted sweep: 12 of 13 green, 9.5 minutes, all 573 components.**

    573/573 components taken through every tab they offer; full sweep
    2,589 tab views exercised
    heaviest component (src/vs/workbench, 47,339 symbols) opened in 1s
    6 lenses exercised: structure, inventory, activity, capability, data, rules
    lens entry times: all 0 to 1s

Only six lenses registered, not eight: VS Code's projection carries neither flow
data nor design signals, and the suite reports what it actually exercised rather
than implying full coverage.

### The one failure, chased to the end

**[#116](https://github.com/sirfifer/solution-explorer/issues/116): symbol search returned nothing on VS Code. Found, diagnosed, fixed.**

The cause was three lines. `SearchOverlay` memoised its results on the query
alone:

    const results = useMemo(
      () => (searchQuery ? search(searchQuery) : []),
      [searchQuery],           // only the query
    );

The search index is module state that GROWS as 85 shards stream in. With no
dependency on the index, a query typed before the shards landed was answered
once against a partial index and never recomputed. Components and files worked
because they come from the manifest and are indexed at boot; all 153,231 symbols
live only in the shards. On a small subject the shards land in milliseconds and
nobody notices. On a 60 MB index it made 91% of the index permanently
unreachable.

`utils/search.ts` now exposes a monotonic index version plus a subscription,
bumped in `rebuildFuse()`, and the overlay includes it in its memo deps.
Verified: the symbol row appears in 2.2 s and is the correct entry.

### And a harder lesson: most of what that failure reported was my test

The same run reported "15 instances of symbol results opening no detail panel"
as a product defect. That was **wrong**, and it briefly went on the public
issue. A symbol result correctly opens the SYMBOL view, which has no
`data-component-id`; my assertion demanded the component panel for all three
result kinds.

The second attempt was wrong too. I asserted that a file result opens a file
view, when `openFileDeepLink` **deliberately** drills to the owning component
and marks the file in its Files tab, written to fix comprehension-study S7 where
landing elsewhere left "the file nowhere in sight". My assertion contradicted an
intentional fix.

Three wrong assertions on one spec, and the pattern is the same each time: **I
asserted what I assumed correct behaviour was without reading what the product
intends.** The code comments documented the design; I had not read them.

Corrected: `FileDetail` and `SymbolDetail` now carry their own `data-testid`
identities, so the crawl can assert each kind against its own contract, and for
a file it additionally checks the second half of the promise, that the file is
visible where the reader lands. Findings went from 17 instances across 3
problems to **1 instance of 1 problem**: a single target of 45 where the search
input never became editable, not yet characterised as deterministic or a race.

**The single most important sentence in this document:** a clean linter is not
evidence that the viewer works. VS Code linted with zero errors while the Rules
lens hung the browser indefinitely and every deep link left the reader with no
row in the tree.

## What was built

| Thing | What it is |
|---|---|
| `scripts/lint-projection.py` | Reads a finished projection end to end: structure, referential integrity, self-consistent counts, every cited file and line checked against real source, completeness heuristics. Proved by 38 mutation tests |
| `viewer/tests/crawl/` | Playwright suite that drives a real browser over a served build. Every expectation derived from the manifest at runtime, so it adapts to any subject |
| `scripts/testboard.py` | The board. Live and historical runs, the demo fleet, version drift, and a glossary so every value on screen carries its own definition |
| `scripts/control.py` | One front door. Always serves the board, exposes a REST API, runs jobs one at a time. Refuses to start enrichment over HTTP |
| `scripts/testboard_emit.py` | Lets the demo pipeline publish processing runs in the same shape the test harnesses use |
| `scripts/issues.py` | The issue ledger: one entry per distinct problem, with instance counts, nature, and traceability back to the run that found it |

## What it found on VS Code

### Fixed

1. **A deep link never revealed its component in the tree.** You arrived at a
   detail panel with no row in the navigator, so no sense of place, no siblings,
   and no way further down without starting again from the top. `expandedIds`
   was local to `TreeNavigator` and nothing reacted to `selectedComponentId`.

2. **The fix for that was itself incomplete, and only VS Code showed it.**
   `collectOtherComponents` adds a component to an "Internal Components" group
   and never recurses into its children, so at depth 5 the thing in the group is
   an ANCESTOR. Matching only the selected id left eleven `extensions/`
   components with no row at all. It passed here because our tree is shallow
   enough that the selected component usually is the grouped one.

3. **The Files tab rendered blank** for a component with zero files instead of
   saying so. A blank panel and a broken panel look identical, and that
   ambiguity teaches people to distrust every empty surface in the product.

4. **The Rules lens hung the browser indefinitely.** This one took three
   attempts and two wrong theories. What settled it was building datasets that
   isolated one variable:

       3745 rules /   1 owner  (panel heavy, graph light)     636ms  ok
        335 rules / 194 owners (panel light, graph heavy)   30255ms  STUCK

   `getLensGraph` never applied the node budget the viewer already had, so the
   lens handed elk 194 nodes and 2,892 edges. Bounding nodes alone was not
   enough, because the kept nodes carry the edges with them: edges are the real
   driver. Now bounded centrally, so no lens can do this again. Full VS Code
   Rules lens afterwards: 1.5 s.

### Open, and needing a decision rather than a fix

- **[#112](https://github.com/sirfifer/solution-explorer/issues/112)**
  `src/vs/workbench` holds 3,625 files and 47,339 symbols in a **50.5 MB**
  detail shard. Originally filed as a defect claiming it was unopenable; that
  was **wrong and has been publicly corrected on the issue**. The lock-up was
  the Rules lens. With graphs bounded it opens in 1.9 s with all 47,339 symbols
  usable. What remains is a real question: is a 50 MB shard acceptable for a
  published demo, and should the deriver split components this large? Note that
  splitting changes component ids, which the demo handoff warns can look like
  mass churn in a projection diff.
- **[#114](https://github.com/sirfifer/solution-explorer/issues/114)** The
  projection republishes `/Users/jrieken/Code/vscode/...` from VS Code's own
  source, a real engineer's home directory. Not ours, trivial to scrub, and
  worth deciding about **before** showing this to anyone at Microsoft.
- **[#115](https://github.com/sirfifer/solution-explorer/issues/115)** A Windows
  temp path from VS Code's source, already carrying a literal `<username>`
  placeholder, so nothing is disclosed. Recorded for completeness.

### Fixed on the publication side

- **[#113](https://github.com/sirfifer/solution-explorer/issues/113)**
  `manifest.root_path` carried the generating machine's absolute path into every
  bundle. Ours, not the subject's. Bundles are now scrubbed at assembly, with a
  note in place of the value; the local projection keeps it.

## Mistakes worth keeping

Recorded because a harness whose failure modes are undocumented gets rebuilt
with the same bugs.

- **Every wait must be one Playwright enforces from Node.** The lens sweep used
  `page.evaluate` to ask whether the page had settled. That takes an argument
  rather than options, so it carries no timeout, and on a main thread spinning
  at 100% CPU it never returns. The budget existed and never fired, and the
  suite hung exactly as the product had.
- **Do not pick the biggest thing as your representative.** The lens sweep chose
  the component with the most files, which on VS Code is `src/vs/workbench`, so
  every lens failed for the same unrelated reason and the sweep proved nothing
  about lenses.
- **Do not measure the wrong axis.** The search spec did a cold page load per
  target, re-fetching and re-indexing a 60 MB search index up to 45 times. The
  case ran past four minutes measuring something no reader ever does. It now
  loads once and moves within the app.
- **Use the serial guard you built.** Two VS Code crawls ran concurrently
  because jobs were started with `npx playwright test` directly instead of
  through `control.py run crawl`. Their timings competed. The board now warns
  when heavy runs overlap.
- **A survey must not abort on its first bad case.** The search sweep threw on
  one uncooperative target, so it never reached its own reporting and the run
  said "1 failed" with zero findings attached. Fixing that revealed 16 further
  problems that the first one had been hiding. Any per-item loop in the crawl
  should record and continue.
- **Adding `role="tab"` broke seven existing tests** by changing the accessible
  role they query by. Caught only by diffing the failing FILE set before and
  after, per the handoff's rule about the viewer's environment-only failures.

## How to run it

```bash
# The front door. Always serves the board, runs one job at a time.
python3 scripts/control.py --open        # http://127.0.0.1:4200/

python3 scripts/control.py run lint     --slug vscode
python3 scripts/control.py run assemble --slug vscode
python3 scripts/control.py run crawl    --slug vscode

python3 scripts/issues.py sync
python3 scripts/issues.py list
python3 scripts/issues.py classify <id> --nature defect --by you --note "why"
python3 scripts/issues.py file <id>          # dry run unless --file
```

Enrichment is deliberately refused over the API. It spends real Claude
subscription usage, so it is started from a Claude Code session and the API
hands back the exact command instead of running it.

## What I would do next

1. **Diagnose and fix #116, symbol search.** It is the most serious open item.
   91% of the search index is unreachable, and search is how anyone finds a
   specific thing in a codebase of this size. Start by checking whether it
   reproduces on this repo's own projection: if it does, it is a matcher bug and
   cheap to find; if it does not, it is scale dependent and probably about
   whether the matcher consults the shard index or only the loaded architecture.
2. **Decide #112.** It is the only open question that touches the shape of the
   published demo.
3. **Scrub subject-embedded absolute paths** (#114) before any outside review.
4. **Run the deterministic pass on a second subject.** Home Assistant or
   Kubernetes will have a different shape of stress, and the pattern so far is
   that each new subject surfaces something the previous one could not.
5. **Then enrichment.** `--profile enriched` on the linter rejects a partial
   enrichment posture, which is the S3 defect class the handoff records, so the
   linter should catch that class immediately rather than after someone notices
   a surface looks wrong.
