  - Design note (resolution order and ambiguity rule).
    - Ownership resolution reads the manifest component `files` arrays ONLY. The per-component `detail-*.json` (fetched lazily) is needed only to obtain symbol line ranges for the `&line=` step, not for ownership.
    - Resolution order: (1) exact path match against `component.files`; collect every component that lists the path. ### P5-4: Git activity extraction (Activity lens data)
- Status: DONE (session program2/p5-activity, Opus 4.8; PR "P5-4: git activity extraction")
- Model: Opus 4.8
- Design: LENS-DESIGN.md sections 4 (L5) and 6; TARGET-ARCHITECTURE.md invariants I2, I4, I6, I7
- Scope: per-file churn series, author contribution shares, and co-change pairs from git log into the store (additive schema_version migration); cached by commit range; ledger-accounted; wholly language-agnostic. No dependency on Phase 5 semantics; may be scheduled immediately after the Phase 4 gate as the first NEW lens data source.

- Elaboration (this session, faithful to the scope above; no scope change):

  Recorded decisions:
  - **Schema (SCHEMA_VERSION 1 -> 2, additive migration).** Four new tables, all with deterministic natural sort keys, keyed by repo-relative git path (not files.id, because git history references deleted and renamed paths that are not in the current files table, and files.id is reassigned every extraction run):
    - `file_activity(path PK, commit_count, lines_added, lines_removed, first_seen, last_modified)` per-file churn totals plus first-seen and last-modified author dates.
    - `file_activity_period(path, period, commit_count, lines_added, lines_removed, PK(path, period))` where `period` is a calendar `YYYY-MM` bucket. Calendar buckets (not "last N days") keep the by-period data byte-deterministic across runs: they depend only on git history, never on wall-clock now().
    - `file_author(path, author_key, author_name, commit_count, lines_added, lines_removed, PK(path, author_key))` author contribution per file. `author_key` is the lowercased email (identity), `author_name` the display name.
    - `cochange_pair(path_a, path_b, cochange_count, PK(path_a, path_b))` with `path_a < path_b`, co-commit counts.
    - Activity provenance in `meta`: `activity_git` (0/1), `activity_shallow` (0/1), `activity_head` (HEAD sha last processed), `activity_commits` (total commits processed), `activity_first_commit` / `activity_last_commit` (author dates).
    - Migration mechanism added to `analyzer/store/db.py`: a `MIGRATIONS` registry in `schema.py` and version-gap application in `_create_schema` (was: raise on any mismatch). A cold store gets all tables from `schema_statements` in one shot; a warm v1 store gets the activity tables via the migration and its `schema_version` bumped to 2. `clear_extraction_facts` does NOT clear the activity tables (like `extraction_cache`, they are the incremental baseline; the activity pass owns their lifecycle).
  - **Extraction unit: one commit = one logical change unit.** Chosen over per-day because it is git-native, deterministic, and unambiguous (no timezone or day-boundary decision). Merge commits are excluded (`git log --no-merges`): `git log --numstat` emits no diff for merges by default, so counting them would only add noise. Co-change pairs are generated only for commits touching at most `MAX_FILES_PER_COMMIT_FOR_COUPLING` (30) files; a commit touching more is a bulk or mechanical change and still counts toward churn and authorship but does not manufacture O(n^2) spurious coupling (the CodeScene cap). Recorded as module constants.
  - **Placement: `analyzer/extract/activity.py` (extraction-adjacent).** It reads `git log`, not source files, so it does not belong in the derive tier (whose zero-source-reads instrumentation guards file opens) and does not violate that rule: git history is environment/provenance, read once at extraction time, exactly as the projection tier is allowed to read `.git` for the repo URL (P4-3 precedent). It runs in `run_v2` after `extract_repo` (it needs the `files` table to know which current paths exist) and before `derive_all`.
  - **Aggregation + projection shape: dedicated `activity.json` shard.** `analyzer/project/activity.py` aggregates per-file activity to component granularity using `store.component_files()` (populated by `derive_all`'s flush, which runs before projection). It emits a dedicated `activity.json` shard (parallel to `coverage.json`) carrying the provenance block, ranked component hotspots with knowledge (author shares, knowledge islands at top-author-share >= 0.95, bus factor as the fewest authors covering >= 50% of commits), ranked component-pair and file-pair coupling above a support floor (`MIN_COCHANGE_SUPPORT` = 2), and per-file detail. A lightweight `activity` summary (top hotspots plus provenance) rides in the manifest like the coverage summary. Monolith mode embeds the full activity dict under an `activity` key. All optional; the viewer ignores them until P6-5 (backward-compatibility test).
  - **Cache by commit range (I6).** `meta.activity_head` records the HEAD sha last processed. A warm run whose HEAD is unchanged processes zero commits (early return, proven by a test). When HEAD advanced and the old head is an ancestor of the new (fast-forward / normal history growth), only `<old_head>..HEAD` is processed and merged additively (all counts are additive over commits, so an incremental merge equals a full reprocess). When the old head is not an ancestor (rebase, force-push, or a shallow boundary shift), the activity tables are cleared and history is fully reprocessed (never a silent partial). Recorded.
  - **Graceful absence.** A non-git root populates no activity tables, records `activity_git=0`, and emits no `activity` projection key (no error). A shallow clone produces truthful partial data with `activity_shallow=1` surfaced in the provenance block, never a pretend-full history.
  - **Ledger accounting.** The pass reads git, not source files, so it adds no `coverage` (file-disposition) rows. It accounts for itself in the `meta` provenance block (git availability, shallow marker, commit count, processed range), which the projection surfaces. This is the honest reading of "ledger-account the pass": the coverage ledger stays a per-source-file ledger; the activity pass states exactly what git history it consumed.
