## 1. Executive summary

The core product is real and in good shape. The analyzer passes 637 tests at 83 percent coverage with ruff clean. The viewer passes 54 tests with a clean TypeScript build. Nearly every feature the docs describe exists in code, including several the roadmap still calls "planned." The vision (help humans comprehend AI-generated codebases, then close the loop by exporting review feedback back to the AI) is coherent, and the architecture serves it.

The gap is in delivery and trust, not in the product:

1. Nothing has ever been published. No git tags, no GitHub releases, no npm package, no PyPI package. The README's flagship `npx solution-explorer` quick start fails for anyone but the author.
2. The April 2026 deploy-blocker fixes (PR #3, commit 2c53835, merged) were incomplete. The live-monitor workflow still fails to parse on every push. A third escaping site in the Cloudflare worker deletes freshly uploaded detail files. The AI-merge script crashes in exactly the scenario it was written to diagnose. The committed AI baseline at the repo root is pytest junk written by a leaky test.
3. One genuine security bug: GITHUB_TOKEN can leak into the published architecture JSON and into CI logs in multi-repo mode.
4. One core-feature bug: split-mode detail panels never render their lazily loaded data.

Summary judgment: the engine is good, the transmission is broken. The remediation plan (WORK-PLAN.md) addresses this in four phases.

## 3. Critical findings

### F-CRIT-1: The distribution story is fiction

README.md line 62 leads with `npx solution-explorer /path/to/your/repo` as "no cloning, no setup." Verified: the package is not on npm (E404), nothing is on PyPI (404), no `v*` tag has ever been pushed, no GitHub release exists, and the README release badge renders "no release." `.github/workflows/release.yml` is well built (tag-triggered, validates the tag against `analyzer/__init__.py`, publishes to PyPI and npm with provenance, moves `latest` and `beta` tags) but has never fired. The action's own warning tells users to pin `@latest`, which does not resolve. `@main` is the only usable ref.

Version chaos compounds this: `analyzer/__init__.py` says 0.3.0 and `packages/cli/package.json` says 0.3.0, but CHANGELOG.md declares 1.0.0 (2025-01-01) and 1.1.0 (2025-02-17) as released, and PROJECT-OVERVIEW.md narrates a shipped v1.2.0. None were tagged or published.

### F-CRIT-2: live-monitor.yml has never parsed; the April fix targeted the wrong layer

`.github/workflows/live-monitor.yml` lines 202 and 240 use `if: ${{ secrets.CF_WORKER_URL != '' }}` at step level. The `secrets` context is not available in step-level `if` expressions, so GitHub rejects the entire workflow file and every push run fails at 0 seconds with "This run likely failed because of a workflow file issue," conclusion failure, zero jobs. This happened before and after commit 2c53835, which added a job-level `vars.LIVE_MONITOR_ENABLED` guard that never gets evaluated because the file never compiles. Proof by contrast: the downstream UnaMentis live-monitor.yml has no step-level secrets `if` and runs green (verified 2026-07-01, 33s).

The same broken pattern ships to every new installation via the init template at `packages/cli/src/templates/live-monitor.yml.ts` lines 11 and 34, so `npx solution-explorer init --live` generates a workflow that never runs.

Two more latent bugs sit behind the parse failure:

- The baseline cache restore uses exact key `arch-baseline-${{ github.ref }}` with no `restore-keys`, while the save key appends the commit sha. The restore can never hit, so the baseline never restores and the AI merge path in this workflow is dead even after the parse bug is fixed.
- `github.event.head_commit.message` is interpolated raw into a triple-quoted Python string in the Notify step (line 282). This is a script injection vector via commit messages (self-repo pushes only, moderate severity).
- The R2 upload step references `.arch-output/data`, which the analyzer step never produces (it writes single-file `--compact`, not `--split`), so the detail upload is dead code in this workflow.

### F-CRIT-3: GITHUB_TOKEN leaks into published output (security)

Path confirmed end to end. `analyzer/multi_repo.py` lines 92-96 rewrite the clone URL to `https://x-access-token:{token}@github.com/...` and clone with it. Git persists that URL in the temp clone's `.git/config`. Then `analyzer/scanner.py` lines 2549-2559 (`_detect_project_info`) read `.git/config`, extract the first `url = ...` with no credential stripping, and store it in `architecture.repository`. `multi_repo.py` line 139 copies it into `merged.repositories[].repository`, which lands in the published architecture.json and, in split mode, manifest.json served by the viewer. A live token ends up in a public artifact.

Related: `multi_repo.py` line 106 prints `result.stderr` verbatim on clone failure. Git's "fatal: unable to access" messages include the credentialed URL, so the token can also leak into CI logs. The success-path print at line 103 correctly uses the untokenized URL. This entire clone path has zero test coverage.

### F-CRIT-4: Split-mode detail panels never render their data

`viewer/src/components/DetailPanel.tsx` lines 129-135: `loadComponentDetail(component.id)` fetches `detail-<safeId>.json` into `componentDetailCache`, but `files` and `symbols` are memoized on `[component.id, getComponentFiles]`. Both dependencies are referentially stable across the cache update (Zustand action identities never change), so the memo never recomputes. The Files and Symbols tabs and their counts stay at the pre-fetch empty values for the currently open component. Nothing remounts the panel. `componentDetailLoading` is subscribed at line 127 but never rendered, so there is no loading indicator either. This breaks the headline split-mode scalability feature end to end. Untested.

### F-CRIT-5: The colon-escape fix missed a third site; the worker deletes fresh uploads

The analyzer (`analyzer/cli.py` `safe_component_id`, line 275) and viewer (`viewer/src/utils/componentId.ts`) now agree on the escape scheme: `/` becomes `--`, `:` becomes `__`. Both carry "must stay in sync" comments and both have unit tests (tests/test_cli.py:556-569, viewer componentId.test.ts). Good.

But `infrastructure/cloudflare/worker/src/index.ts` line 311 (`cleanupOrphanedDetails`) still computes active keys with only `id.replace(/\//g, "--")`. With multi-repo IDs like `repo:unamentis`, CI uploads `detail-repo__unamentis.json`, the worker computes `detail-repo:unamentis.json` as the active key, and deletes every freshly uploaded detail file as orphaned on the next `/ingest`. The commit message for 2c53835 claimed "the two sides cannot drift," but there were three sides.

### F-CRIT-6: The AI-merge diagnostic crashes in its own target scenario (reproduced)

In `scripts/merge-ai-enhancements.py` `main()`, `baseline_index` is only assigned (line 135) when the baseline lacks architecture-level `ai_enhance`. The 0-matches diagnostic added by 2c53835 (line 167) references it unconditionally. Since `/ai-assist` always writes architecture-level `ai_enhance`, the exact scenario the diagnostic targets (AI-enhanced baseline, zero components matched due to ID drift) raises UnboundLocalError and exits 1. Reproduced locally: exit 1. The AI-stripped target file has already been written (line 149) before the crash, so the step fails with a confusing traceback after mutating the file. The underlying design gap remains: the merge matches on exact IDs only and does nothing to remap drifted IDs, so the original data-loss mechanism is still live.

### F-CRIT-7: The committed AI baseline is pytest junk, written by a leaky test

`tests/test_cli.py::test_max_symbols_explicit_override` (line 348) calls `main()` without `-o`, so the analyzer writes the default `architecture.json` into the current working directory. Running pytest from the repo root silently clobbers the repo-root `architecture.json`, which is the AI-enhancement baseline that architecture-viz.yml merges from. Verified: both the committed version and the current working-tree version contain pytest temp paths as `root_path` (pytest-11 and pytest-4 respectively). The upstream baseline therefore contains no real AI data. This is very plausibly the true origin of the April "0/253 components preserved" symptom, and it will recur on the next `git add -A`. The current dirty working-tree change must not be committed as-is.

### F-CRIT-8: Incremental mode silently drops files it cannot map

`analyzer/incremental.py` lines 911-929 (`map_files_to_components`): a changed file not in the baseline file index falls back to a parent-directory walk (`for i in range(len(parts)-1, 0, -1)`) that never checks the root component (path "") and matches nothing for unknown directories. A new root-level file or a new directory maps to zero affected components. Neither `should_full_rescan` (lines 948-984) nor `_run_incremental` detects the miss, so the incremental output silently omits new files. This violates the 100 percent coverage principle in the mode designed for CI. No test covers the unmapped-changed-file scenario.

## 4. Analyzer findings (Python)

### F-AN-1: Repeated full-file disk re-reads and O(n squared) lookups in relationship detection

The main large-repo performance trap. `_read_component_code` (scanner.py:1646-1671) does a linear scan of `self._all_files` per file and re-reads every code file from disk. It is called once per component in each of the websocket, grpc, database, and message-queue detectors (scanner.py:1680, 1718, 1764, 1808) and again per HTTP relationship for both source and target in `_enrich_existing_relationships` (1875, 1895). A single file can be read from disk six or more times. `_detect_relationships` additionally re-reads every code file three more times in the port-scan (1211), service-name (1279), and external-API (1496) loops; the service-name loop runs up to five regex searches per service-file pair. `_assign_server_ports` (958-1034) is O(server components times all files) with disk reads. `_compute_component_metrics` (1960-1967) linearly scans `_all_files` per component file. A single content cache dict plus a `{path: FileInfo}` index removes all of this without behavior change. On a 10,000-file monorepo this is the difference between seconds and many minutes.

### F-AN-2: `_check_ci_tests` walks above the repository root

scanner.py:2269-2302: starting at the component directory, it climbs up to 10 parent levels checking CI configs, stopping only at the filesystem root, never at `self.root`. Scanning `/Users/x/dev/project` reads `/Users/x/dev/.github/workflows`, `/Users/x/.github`, and so on. Consequences: `has_ci_tests` can be true from an unrelated outer repo, and a static-analysis tool reads files outside the target tree.

### F-AN-3: Silent symbol truncation and inconsistent stats

Single-file mode sorts and slices symbols to the 5,000 default cap with no warning printed anywhere (scanner.py:153-166, cli.py). Worse, `stats.total_symbols` is set from the untruncated count (scanner.py:172) while the `symbols` array is truncated, so the viewer's stats disagree with its own data. Files over 500 KB are skipped with a bare `continue` (scanner.py:505-508, no log). See also F-DC-2: the two paths users are told to run first (npx CLI, build.sh) are the capped ones.

### F-AN-4: Escape scheme edge cases

`safe_component_id` (cli.py:275-286) is not injective: IDs `a/b` and a literal `a--b` collide to the same detail filename, producing silent detail-file overwrites in split mode. Its own docstring lists `" < > | * ?` as forbidden by upload-artifact, yet only `/` and `:` are escaped. Similarly `_make_component_id` (scanner.py:2608-2612) lowercases and maps spaces to `-`, so directories `Foo Bar` and `foo-bar` collide. Edge cases, but silent when they hit.

### F-AN-5: Malformed multi-repo config crashes with a raw KeyError; clone has no timeout

multi_repo.py:46 accesses `repo_def["name"]` directly. A repo entry without `name` raises KeyError instead of the friendly `sys.exit` used elsewhere in the same method. The clone `subprocess.run` (line 104) has no timeout.

### F-AN-6: Unguarded `iterdir()` can abort the scan

scanner.py:677-679 and 688-691: `comp_dir.iterdir()` and `parent_dir.iterdir()` inside `_classify_architectural_role` have no OSError handling. An unreadable directory raises PermissionError and aborts the whole scan. Everywhere else file IO is defensively wrapped; these spots are the exception.

### F-AN-7: Tree-sitter fallback silently swallows all exceptions

tree_sitter_base.py:22-35: `except Exception: pass`, then regex fallback. Files that crash tree-sitter get regex-extracted symbols in the same run with different granularity (for example, SwiftTreeSitterParser extracts nested methods, the regex SwiftParser only functions at indent 4 or less) and no log line. Parity tests exist per language but cover happy paths only. At minimum, log the fallback at debug level so parity drift is diagnosable.

### F-AN-8: Dead code

`SwiftParser.SYMBOL_PATTERNS` (swift.py:14) and `RubyParser.SYMBOL_PATTERNS` (ruby.py:13) are defined but never referenced. `UIActionDetector.SWIFTUI_BUTTON_ACTION_RE` (action_detector.py:20) is never used. incremental.py carries roughly 450 lines of deprecated functions (`rescan_component`, `merge_component_into_baseline`, `redetect_relationships`) exercised only by their own tests.

### F-AN-9: CLI flag conflicts silently ignored

cli.py:112-190: the `--incremental` branch returns before split handling, so `--incremental --split` silently ignores `--split`. `--config` similarly wins over `--incremental`. These should be argparse errors.

### F-AN-10: Split mode never deletes stale detail files

`write_split` (cli.py:289) only adds files. Removed components leave orphan `detail-*.json` in `data/` on redeploy.

### F-AN-11: Known regex fragility in SwiftUI flow detection

`[^}]*?` in NAV_LINK_CONTENT_RE, SHEET_RE, NAV_DEST_RE, TAB_ITEM_LABEL_RE (swiftui_flow.py:46-76) stops at the first closing brace, so a destination after any nested closure is missed. `_extract_view_body` falls back to whole-file content when the struct regex misses (line 112), reintroducing the cross-view contamination the method exists to prevent. Accepted-by-design fragility; documented here for awareness.

### F-AN-12: Miscellaneous

- `detect_ports` clap pattern (parsers/base.py:73): `default_value = "8080"` matches any 4-5 digit clap default, not just ports; likely the root of the xfailed test.
- Windows path mismatch in scoped/incremental mode: baseline paths use `/` while `_component_map` keys split on `os.sep` (scanner.py:2628-2637). Harmless on POSIX, broken on Windows.
- `_apply_changelog` builds an IncrementalAnalyzer via `object.__new__` (cli.py:263). Works today, fragile against refactors.
- `analyzer_version` is hardcoded "1.0.0" in analyzer/models.py:308 and 422 while the package version is 0.3.0.
- scanner.py is 2,666 lines in effectively one class. The 11 relationship strategies and the testing/docs extraction are natural split seams. incremental.py is 1,446 lines, about 450 of them deprecated.

### Analyzer strengths worth preserving

Green suite with honest xfail marking, clean ruff, fast run (1.5s). The scoped-scanner architecture (scope_paths plus baseline on ArchitectureScanner) lets incremental mode reuse the full pipeline rather than duplicating logic. The tree-sitter upgrade pattern (regex baseline, per-language independent optional upgrade, delegation of non-symbol methods to regex parsers) keeps the stdlib-only-core promise, with parity tests. Defensive IO discipline is otherwise strong (`errors="replace"`, OSError guards nearly everywhere). Symbol prioritization under max_symbols is sensible. Distance-based BFS tab assignment and per-view-struct body extraction in swiftui_flow show careful iteration on real failure modes. Incremental analysis is tested against real git repos (test_incremental.py, test_dpea.py run git via subprocess). All six tree-sitter parsers are tested, including regex-parity tests.

## 5. Viewer findings (React/TypeScript)

### F-VW-1: Split-mode stale memo

See F-CRIT-4.

### F-VW-2: popstate handler corrupts back/forward history

App.tsx:321-366. The store subscription (lines 322-341) calls `pushUrlState` on every drillLevel change. The popstate handler (lines 344-366) calls `drillInto` or `navigateToBreadcrumb`, which change drillLevel, which re-fires the subscription and pushes a new entry mid-popstate. Pressing Back re-pushes the state you just navigated to and destroys the forward stack. No suppression flag exists.

### F-VW-3: Live refresh permanently wipes lazily indexed search entries

useLiveMonitor.ts:165 plus search.ts:18 plus store.ts:574-577. Every manifest poll calls `initializeSearch(data)`, which resets `allResults = []`, dropping symbols and files added via `addToSearchIndex` from split-mode detail loads. They are never re-added because `loadComponentDetail` early-returns on a `componentDetailCache` hit. After the first live update, previously loaded symbols disappear from search until a full page reload.

### F-VW-4: Review annotations are memory-only

store.ts:145, 300, 423-454. Dark mode, changelog read-state, enhanced-frames, and help-dismissed all persist to localStorage; annotations do not. A page refresh, or following one of the product's own shareable deep links, destroys all review work. This is the most damaging single gap for the close-the-loop vision. PROJECT-OVERVIEW.md line 157 says indicators "persist across the session," which is technically true and reads as "survives reload" but does not. Zero tests cover annotations or promptGenerator.

### F-VW-5: Per-poll performance cliff in status overlay

store.ts:472: `applyStatusOverlay` deep-clones the entire component tree via `JSON.parse(JSON.stringify(...))` on every overlay poll and rebuilds an index that is never used (line 469, lint-confirmed dead). All node identities change, so React Flow re-renders everything each poll. It also strands `detailItem.data` pointing at the old tree, so an open detail panel shows pre-overlay data.

### F-VW-6: ComponentNode subscribes to the whole store

ComponentNode.tsx:746: no selector, so `memo` is defeated for store changes. Every node re-renders on any store mutation and re-filters `architecture.relationships` twice per node (lines 749-750). O(nodes times relationships) per store change. Together with main-thread elk.bundled.js, this is the main large-graph performance risk.

### F-VW-7: Miscellaneous confirmed bugs

- Literal HTML entity rendered as text: App.tsx:649 renders the JS string `"&#x25B2;"` inside a JSX expression, so the summary toggle shows raw entity text. Sibling usages as JSX text (line 657) are fine.
- Initial-load race: App.tsx:253-295 calls `setArchitecture` unconditionally while useLiveMonitor may have already loaded fresher live data. Last write wins; `initializeSearch` also runs twice.
- Poll timer re-arms while hidden: useLiveMonitor.ts:234-243 clears the timer on hide, but an in-flight `poll()` that completes after hiding calls `scheduleNext` unconditionally. `poll` and `scheduleNext` never check `document.hidden`.
- ELK layout race: ArchitectureGraph.tsx:233-259 has no staleness guard, so an older layout promise resolving last can set stale nodes after rapid drill navigation. The selection-centering effect (267-293) can run before ELK resolves and pans to pre-layout grid positions on URL deep-link restore.
- Detail-fetch failures are swallowed (store.ts:585-602): no error state surfaced, no negative caching, so every re-open refires a 404. Two simultaneous loads for different components both clear `componentDetailLoading` unconditionally.
- The `?tab=` URL param written by DetailPanel (59-63) is erased by App's URL subscription (328-331), which rebuilds the URL with only component and drill.
- Live refresh does not invalidate `componentDetailCache`, so stale symbols and files persist across architecture updates until reload.
- localStorage architecture cache (useLiveMonitor.ts:169) has no schema or version key, so a stale cache from an older schema renders before the fresh fetch corrects it. Quota failures are handled.

### F-VW-8: Bundle and structure

Single 2.1 MB chunk (630 kB gzip); bundled elkjs and React Flow dominate. `search.ts` is imported statically in App.tsx:17 and dynamically in store.ts:594, which defeats code splitting (Vite warns). File sizes: DetailPanel.tsx 1,675 lines (about 9 tab components in one file), ComponentNode.tsx 1,100 (about 700 lines of device-frame markup plus logic), App.tsx 900, store.ts 846. Lint confirms 19 unused vars, including an entire unused destructure block in DetailPanel (48-51) and the dead index build in store.ts:469.

### F-VW-9: Test coverage reality

4 test files, 54 tests, touching roughly 4 of about 27 source modules. Well tested: store navigation (drill-down, breadcrumbs, hero-filter fallback, navigateToComponent), useLiveMonitor pure helpers (interval math, circuit breaker), componentId escaping, ErrorBoundary. Untested critical paths: `loadComponentDetail` split-mode fetch and caching (where F-CRIT-4 and F-VW-3 live), the actual polling loop and visibility handling, urlState plus App's URL sync and popstate (F-VW-2), search init/add/rebuild, promptGenerator review export, annotation actions, changelog read-state persistence, and every UI component except ErrorBoundary.

### F-VW-10: Repo hygiene

`viewer/coverage/` (a vitest HTML report) is committed to git and not gitignored. `viewer/test-results/` exists and is not ignored. `packages/cli/dist/` has 18 committed build artifacts. Root `architecture.json` is tracked despite matching a root .gitignore entry (tracked files win over ignore rules), and is currently dirty with pytest junk (F-CRIT-7).

### Viewer strengths worth preserving

Clean tsc, zero production-dependency vulnerabilities, fast suite. Store navigation logic is genuinely well tested including edge cases. The analyzer/viewer filename-escaping contract is documented and tested on both sides. Consistent defensive patterns: `isJsonResponse` guard against SPA HTML fallback, try/catch around all localStorage access, `ai_enhance?.` optional chaining applied consistently so non-enhanced JSON degrades cleanly. The live monitor design (ETag conditional GET, adaptive intervals, circuit breaker, visibility pause, 30-minute full refresh) is thoughtful, and its pure-function extraction made it partially testable. Changelog read tracking uses a compact watermark-plus-sparse-set structure that self-collapses, bounded by design.

## 8. Where the project is meant to be

Restating the destination so the plan has a fixed target:

1. A stranger runs `npx solution-explorer /path/to/repo` and it works, uncapped, with the current viewer.
2. A maintainer pushes to main and every workflow is green, deploys preserve AI enhancements without hand-holding, and downstream installs stay in sync.
3. A reviewer annotates an architecture, closes the laptop, comes back, and the annotations are still there; the exported prompt round-trips into an AI session; the AI can link back into the viewer at file and line granularity.
4. Every documented claim is true, every test asserts real behavior, and silent truncation or silent data loss does not exist anywhere in the pipeline.

The remediation plan in [WORK-PLAN.md](WORK-PLAN.md) is organized around exactly these four outcomes.
