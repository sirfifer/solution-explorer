# P10-3 Design: Stakeholder Views (business, executive, support)

Delivered 2026-07-20 as the card's design pass. Phasing at the end; the owner
green-lights increments.

## 1. The audiences, made concrete

Verdict key: TODAY (answerable from current rules/capabilities/entities/
enrichment), NEW (needs a named deterministic derivation), CANNOT (not
honestly answerable from the repo alone).

(a) Executive / business stakeholder
1. "What can this system do for customers?" TODAY: capabilities named in
   business terms by enrichment.
2. "What business rules does it enforce?" TODAY partly: the Rules lens
   exists, but its statements are mechanical, not business language
   (section 2).
3. "How much of this is ours versus bought?" TODAY once P10-1 SBOM lands;
   NEW is only the executive framing over it.
4. "What are the biggest risks in this asset?" TODAY as findings/concerns
   exist, but business-risk ranking is CANNOT without impact data the repo
   lacks.
5. "What would it cost to change X?" CANNOT: blast radius is a size proxy,
   not a cost.
6. "Is it compliant or secure enough?" Partly TODAY via P10-2/P10-4 hygiene
   checks, but a compliance verdict is CANNOT.

(b) Support engineer
1. "Where is this configured?" TODAY: env_var signals plus detected config
   and manifest files, grouped per component.
2. "What does this talk to that I do not control?" TODAY: http_client,
   websocket_driver, port, external services.
3. "What are the entry points a ticket could touch?" TODAY: capabilities
   (endpoints, CLI, jobs).
4. "What data does this handle?" TODAY: entities plus enrichment
   data_handled.
5. "What could make this break at 3am?" NEW: a bounded, ranked
   deterministic derivation over the three signal families above
   (section 4).
6. "How do I know a fix worked?" TODAY via capability-to-test linkage,
   honestly marked inferred.

(c) Product manager
1. "What features exist and are they tested?" TODAY: capabilities with test
   linkage and coverage.
2. "What changed recently and where is churn?" TODAY: Activity lens.
3. "Who knows this area?" TODAY: knowledge map (bus factor).
4. "Where is duplicated or diverging work?" TODAY: clone clusters and
   concerns.
5. "What is unfinished or orphaned?" TODAY: unreferenced findings, honestly
   marked uncertain.
6. "What is the roadmap?" CANNOT: intent lives in trackers, not the repo.

The PM audience is almost entirely served by existing lenses with a
relabeling. It needs no new build, only an audience preset.

## 2. The translation problem

The Rules lens carries a MECHANICAL summary by design (condition text and
outcome, invariant I1). "reject when order.total < MIN_ORDER" is code
vocabulary, not "orders below the minimum are declined." Closing that gap
has two layers. First, deterministic normalization already available: kind
labels (validation, calculation, policy, io) map to business verbs (checks,
computes, decides, constrains); the linked entity and field names supply the
nouns; the linked capability supplies the trigger ("during checkout"). That
gets a readable skeleton with zero AI.

Second, real translation is an enrichment overlay authored ONCE into the
projection (I1/I9), never at query time, provenance-stamped and drilling to
the cited lines. This is a NEW enrichment target: a business_statement field
on each rule, generated by the same pass that writes rule statements today,
verified against its evidence by the P7 adversarial check.

Where translation is genuinely impossible: the repo contains the mechanism,
not the WHY. A threshold constant of 500 has no business meaning the code
can reveal. The view must say so. Any rule whose statement depends on a bare
literal or an unexplained domain constant is rendered with the value shown
and a visible "needs a human: business meaning of this value is not in the
code" marker, not a fabricated rationale. This is the anti-theater rule for
section 2.

## 3. Hiding without lying

Audience is a PRESET over the existing lens switcher, not a new lens tree.
A preset does three deterministic things: selects which lenses are visible,
sets default labels (business verbs versus mechanical), and sets a
surface-reduction level that hides file paths, symbol names, and code
snippets from the default render. Nothing is deleted from the data. Every
reduced element carries a persistent "show me the machinery" affordance that
drops the reader into the full technical lens on the SAME element (I12
stable identity). The door is always present and never locked. The executive
preset hides the most; the support preset hides paths but keeps config keys
and endpoints; the PM preset hides almost nothing. Presets are URL state, so
a shared link opens in the sender's audience.

## 4. The support view

Built entirely from existing signals, one ranked landing (I11):
- Configuration surface: distinct env_var names per component, plus detected
  config and manifest files, each drillable to the read site. KEEP.
- External dependencies: http_client and websocket_driver call sites, port
  bindings, external services, bridging to the SBOM. KEEP.
- Entry points: capabilities as the ticket-facing surface. KEEP.
- "What could break at 3am": a ranked list = external dependencies (things
  outside the process) + required configuration (env vars read with no
  visible default) + entry points, each with evidence. The one NEW
  derivation, honest because every member is a real signal. KEEP as
  P10-3a's centerpiece.
- Error-handling density: KILL. A count of try/except blocks does not
  predict failure and reads as insight while being noise.

## 5. Value test verdict

KEEP: support view (all four surfaces above), PM audience preset,
business-verb normalization of rules, the machinery door.
BUILD-WITH-ENRICHMENT: business_statement rule overlay. KILL:
error-handling density; blast-radius-as-cost; any business risk score.
DEFER: the standalone executive dashboard. An executive surface today can
only restate technical facts in vague business words, which is the precise
theater the owner rejects. What would change the answer: a real named
executive stakeholder posing questions the current lenses miss, or an
external mapping (tickets, incidents, revenue-by-feature) fed in as
evidence. Until then the executive is served by the business-language Rules
and Capability lenses under a reduced preset, not by a dashboard.

## 6. Phasing

P10-3a (build now, no new enrichment): the Support view including the
ranked "what could break" derivation; audience presets (executive, support,
PM) as lens-visibility plus surface-reduction plus label sets over the
existing switcher; the machinery door; business-verb normalization of rule
kinds using entity and capability links.

P10-3b (needs an enrichment pass): the business_statement rule overlay with
the "needs a human" marker for unexplained constants, gated by the P7
verification pass.

P10-3c (deferred, evidence-gated): any dedicated executive dashboard, held
until a real stakeholder produces questions the presets cannot answer.
